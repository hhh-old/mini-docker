# OCI Manifest 中 Layers 每一层是怎么来的

## 一、层的来源：Dockerfile 中的每条指令

Docker 镜像是**逐层构建**的，Dockerfile 中的几乎每条指令都会产生一个新层。举个例子：

```dockerfile
FROM alpine                        # 层 0: alpine 基础系统
RUN apk add python3                # 层 1: 安装 python3
COPY app.py /app/                  # 层 2: 复制应用代码
RUN echo "v1" > /app/version.txt   # 层 3: 写入版本文件
RUN rm /app/version.txt            # 层 4: 删除版本文件（产生白标）
RUN echo "v2" > /app/version.txt   # 层 5: 重新写入版本文件
```

构建时，Docker 为每条指令做：
1. 基于上一层启动一个临时容器
2. 执行指令（RUN/COPY/ADD 等）
3. 用 OverlayFS 的 upper 层记录所有文件变更
4. 将 upper 层打包成 tar.gz → 这就是 Manifest 中的一个 Layer

所以上面的 Dockerfile 会产生 6 层，Manifest 中 `Layers` 数组就有 6 个元素。

## 二、每层都有文件吗？

**不是的。** 层分为两种：

| 指令类型 | 是否产生文件层 | 说明 |
|----------|---------------|------|
| `RUN` | 是 | 执行命令产生的文件变更 |
| `COPY`/`ADD` | 是 | 复制/添加文件 |
| `ENV` | 否 | 只改元数据，不产生文件层（History 中标记 `empty_layer: true`） |
| `EXPOSE` | 否 | 只声明端口 |
| `WORKDIR` | 否 | 只改工作目录 |
| `VOLUME` | 否 | 只声明卷 |

不产生文件层的指令只会写入 `History` 数组，不会在 `Layers` 中出现。所以 **Manifest 中 `Layers` 的每一层都有实际的文件内容**（tar.gz 非空）。

## 三、.wh 白标文件是怎么来的

关键问题：Docker 的层是**叠加**的，那"删除"操作怎么表达？

```
层 3: 写入 /app/version.txt（内容 "v1"）
层 4: 删除 /app/version.txt
```

层 4 的 tar 包里不可能有一个"空"的 version.txt（那是覆盖，不是删除），也不可能什么都不放（那就等于 version.txt 还在）。

**OCI 规范的解决方案：白标文件（Whiteout）**

Docker 在构建层 4 时，检测到 `/app/version.txt` 被删除了，就会在层 4 的 tar 包里放入：

```
/app/.wh.version.txt    ← 一个空文件，名字以 .wh. 开头
```

这个文件就是一个"删除标记"，告诉容器引擎："在叠加层时，把下层的 `version.txt` 删掉"。

### 白标文件的两种类型

**1. 普通白标：`.wh.<filename>`**

删除下层中特定文件/目录：

```
# 层 3 的 tar 内容：
app/version.txt          ← 正常文件

# 层 4 的 tar 内容：
app/.wh.version.txt      ← 白标：删除下层的 version.txt
```

**2. Opaque 白标：`.wh..wh..opq`**

隐藏该目录下所有下层文件：

```dockerfile
FROM alpine
RUN mkdir -p /app && echo "old" > /app/a.txt && echo "old" > /app/b.txt
RUN rm -rf /app/* && echo "new" > /app/c.txt
```

层 2 的 tar 内容：

```
app/.wh..wh..opq     ← opaque 白标：清空该目录下所有下层文件
app/c.txt            ← 本层新增的文件
```

这样叠加后，`/app/` 目录下只有 `c.txt`，`a.txt` 和 `b.txt` 都被隐藏了。

### Opaque 白标的处理顺序问题

同一层内如果同时有 `.wh..wh..opq` 和新增文件（如 `c.txt`），处理顺序不影响结果：

- `.wh..wh..opq` 的语义不是"清空这个目录"，而是**"隐藏这个目录下所有来自下层的文件"**
- `c.txt` 是本层新增的文件，不属于"来自下层的文件"，所以不会被 opaque 白标影响
- 代码中 `filepath.Walk` 按字典序遍历，`.wh..wh..opq` 排在 `c.txt` 前面，先处理白标再写入新文件

## 四、完整的层叠加流程

以最初的 Dockerfile 为例：

```
层 0 (alpine):  bin/sh, etc/, lib/, ...     ← 基础系统
层 1 (apk add): usr/bin/python3, lib/...    ← 新增 python 文件
层 2 (COPY):    app/app.py                  ← 新增应用代码
层 3 (echo):    app/version.txt ("v1")      ← 新增版本文件
层 4 (rm):      app/.wh.version.txt         ← 白标：删除 version.txt
层 5 (echo):    app/version.txt ("v2")      ← 新增新版本文件
```

叠加时从底层到顶层逐层处理：

```
层 0 → 层 1 → 层 2 → 层 3 → 层 4 → 层 5
                                         ↓
最终 rootfs:
  bin/sh, etc/, lib/...           ← 来自层 0
  usr/bin/python3, lib/...        ← 来自层 1
  app/app.py                      ← 来自层 2
  app/version.txt ("v2")          ← 来自层 5（层 3 被层 4 白标删除）
```

## 五、对应到 mini-docker 代码

在 `doPullFromRegistry` 中：

```go
for i, layerDesc := range manifest.Layers {
    // 下载每一层的 tar.gz blob
    blobPath, _ := client.DownloadBlob(repository, layerDesc.Digest, blobProgress)
    // 解压到 overlay2/<cache-id>/diff/，白标文件也保留在 diff/ 中
    cacheID, _ := layerStore.StoreLayer(blobPath, layerDesc.Digest, diffID)
}
```

在 `BuildRootFS` → `overlayDiffToRootFS` 中：

```go
// 遍历每层 diff/，叠加到 rootfs
if strings.HasPrefix(baseName, ".wh.") {
    // 遇到白标文件：删除 rootfs 中对应的文件，白标本身不写入 rootfs
    os.RemoveAll(whiteoutTarget)
    return nil
}
// 遇到普通文件：覆盖写入 rootfs（上层覆盖下层）
```

白标文件是 OCI 规范在**只追加**（append-only）的分层模型中表达"删除"的唯一方式——你不能修改下层，只能在上一层放一个标记说"删掉它"。
